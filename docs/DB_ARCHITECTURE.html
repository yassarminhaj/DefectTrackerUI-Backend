A table-by-table reference for the Defect Tracker PostgreSQL schema. Phase1 (foundation)

Overview

The Defect Tracker is a Flask + PostgreSQL application that manages the full defect lifecycle for QA / fintech teams. The database is organised into four logical groups:

Identity & Access — who can log in and the audit of password changes. Master / Reference Data — the configurable lists every defect is classified against (projects, environments, releases, severities, priorities). Workflow Engine — a versioned status diagram and the allowed status-to-status transitions generated from it. Core Defect Records — the defect itself plus its inline images, file attachments, comments, and an immutable history/audit trail.

Every operational mutation flows through the REST API under /api/v1; the static UI pages in app/ui_static/ call those endpoints through the apiFetch() helper in js/app.js. No UI screen writes to the database directly.

Global mechanics that shape writes

Authentication

All /api/v1 routes except login, refresh and health require an Authorization: Bearer live.<userId>.<token> header (Phase 1 demo tokens). The decoded user id becomes the actor stamped into created_by_user_id / updated_by_user_id and history actor columns.

Data context (Test / Prod / All)

The X-Data-Context header (falling back to app_users.default_data_context) scopes defect reads to environments whose environment_scope matches. It filters reads; it does not change which columns get written.

Soft deletes

Tables that support deletion (defects, defect_attachments, defect_inline_assets, defect_comments) are never hard-deleted by the API. A DELETE sets is_deleted=true plus deleted_at / deleted_by_user_id where present.

Automatic audit trail

The backend helper add_history() writes a row to defect_history_events on every defect-related mutation. Users never write to that table directly — it is a side effect of other endpoints.

Audit stamp columns

Most tables carry created_at, created_by_user_id, updated_at, updated_by_user_id. These are set automatically by the API (timestamps via now(), user ids from the bearer token) and are not user-editable form fields.

Design notes

The bearer token format is live.<id>.<random>; the user id is parsed straight from it (Phase 1 demo auth). Email and username uniqueness are enforced case-insensitively in the validator and by unique constraints. Self-referencing created_by/updated_by FKs allow the first seeded admin to reference itself.

Phase 1 note — release fields live on the defect

The current static UI captures the fix release through typed fields on the defect (defects.release_version, defects.release_deployment_date) entered on the defect-edit screen, rather than always linking to a releases row. The releases master table is still maintained via the API and back-fills older rows linked through fixed_in_release_id (see ensure_runtime_schema()). There is no dedicated static "Releases" CRUD page in Phase 1; management is done through the API playground.

Status-driven write rules (PATCH)

A status change is rejected unless the target appears in the active workflow's allowed transitions from the current status. When moving to Fixed, release_version, release_deployment_date and fix_date become required. When moving to Closed, closure_date is required and must be on/after fix_date. fix_date cannot be in the future. Each changed column emits a typed history event (status_changed, assignment_changed, severity_changed, priority_changed, release_updated, or generic field_updated) sharing one event_batch_id.
